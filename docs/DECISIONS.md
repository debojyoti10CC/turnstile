# Decisions

| Date | Decision | Alternatives | Reason |
|---|---|---|---|
| 2026-09-11 | Channel boxes are never deleted | Delete on close + tombstone | Deleting resets totalClaimed → replay of old vouchers on re-fund. Salt gives fresh channels |
| 2026-09-11 | claim = accounting, settle = sweep | Transfer per claim | Mirrors EVM binding; one transfer for many channels |
| 2026-09-11 | Stale claim rows are no-ops | Revert | Idempotent settler retries; one bad row shouldn't sink a batch |
| 2026-09-11 | Withdraw delay in seconds (latest_timestamp), 900–2,592,000 | Rounds | Same units/bounds as EVM & SVM bindings |
| 2026-09-11 | payerAuthorizer may also start/finalize withdrawals | Payer only | Funds always go to payer, so hot key gains no theft path; lets agents exit without the cold key |
| 2026-09-11 | No voucher expiry | expiresAt field | SVM binding requires expiresAt = 0 for the same reason: withdraw delay already bounds redemption |
| 2026-09-11 | escrow-client/tests build every app-call's box/account/asset references explicitly and disable algokit_utils's simulate-based auto-population (`populate_app_call_resources`/`cover_app_call_inner_transaction_fees: False`) | Rely on `allowUnnamedResources` auto-discovery per CLAUDE.md §7 | On this algod 4001/algokit_utils 4.2.3 pairing, letting the composer auto-discover resources for an ABI *method call* (as opposed to a bare app call) intermittently routes through an internal fee-probe codepath that submits a synthetic create+delete "op-up" stub transaction and misreports a `group fee too small` error instead of the real missing-resource error. Explicit refs are deterministic and match what a production facilitator would compute anyway (CLAUDE.md already calls for simulate-based *discovery*, not blind reliance at submit time) |
| 2026-09-11 | `claim()`'s extra fee is computed as `ceil(n * 2600 / 700) * minFee` | Flat `1 * minFee` guess | Matches CLAUDE.md §1's op-up formula exactly: n=1 row needs `ceil(2600/700)=4` op-up inner transactions, each consuming one network min-fee from the pooled group credit. Verified empirically on LocalNet — 3 op-ups (3000 µAlgo) under-funds and fails with `group fee too small`; 4 (4000 µAlgo) succeeds |
| 2026-09-11 | LocalNet dev-mode timestamp-offset tests submit one throwaway 0-amount payment immediately after `algod.set_timestamp_offset()` before the time-sensitive call | Call the time-sensitive method directly after setting the offset | Empirically, algod only applies a newly-set dev-mode offset starting from the block *after* the one it was set on — the very next submitted transaction still sees the old effective timestamp. A harmless "latch" transaction (unique note, to avoid `TransactionPool.Remember: transaction already in ledger` on repeat calls) forces that extra block so the following call sees the advanced clock |
| 2026-09-11 | `packages/x402-avm-batch` pins `@algorandfoundation/algokit-utils` to the stable ^9.2.2 line (via `@turnstile/escrow-client`), not the `10.0.0-alpha.46` version `.refs/x402`'s own `@x402/avm` package uses | Match `@x402/avm`'s exact algokit-utils version per CLAUDE.md §3 ("match the major used by @x402/avm") | `@x402/avm`'s `signer.ts`/`utils.ts` depend on subpath exports (`/algorand-client`, `/crypto`, `/transact`, `/common`) that only exist on algokit-utils's unreleased "decoupling" alpha branch — no stable release, undocumented, breaking-prone. `@turnstile/escrow-client` is already built, tested against real LocalNet transactions, and pinned to the stable 9.2.2 API; `@x402/core`'s `SchemeNetworkClient`/`SchemeNetworkServer` interfaces (what we actually implement) are stable at 2.25.0 and carry no algokit-utils version coupling, so there is no real requirement to match `@x402/avm`'s internal dependency choice. Logged here as a deliberate, documented deviation rather than a silent drift |
| 2026-09-11 | P2 (`x402-avm-batch`) scope for this pass: implement `ChannelStorage` (in-memory, per-channel async lock), a channel manager with the exact charge/signed-max rule checks (I9), server `SchemeNetworkServer` hooks for verify/settle, and a client `SchemeNetworkClient` for payload creation + corrective-402 adoption with signature re-verification (I11). Skip the EVM reference's `pendingRequest`/TTL reservation system and its auto-settlement interval runner | Port every EVM file line-for-line (channel manager's auto claim/settle/refund loop, TTL-bounded pending-request reservations, ~600-line verify.ts/settle.ts) | The EVM reference is ~40 files / 3,000+ lines for client+server alone, much of it either P4's concern (the settler's claim/settle/refund loop lives in EVM's `channelManager.ts`, which this repo's phase plan assigns to `packages/settler`) or a throughput optimization (the pending-request reservation avoids holding a lock across arbitrary handler execution time, but isn't required for *correctness*: a single atomic `storage.updateChannel` at charge-commit time that rechecks `newCharged <= signedCap` and `<= mirrored balance` preserves I9/I12 without it, at the cost of rejecting overlapping same-channel requests only after their handler runs instead of before). Revisit the reservation system if the no-reservation approach proves a measurable bottleneck under the P3 demo's concurrency. |
| 2026-09-11 | P3 demo: the client/agent submits its own deposit transaction group directly (via `@turnstile/escrow-client`, its own keys) before sending the x402 payload; the facilitator's `verify()` for a deposit payload only confirms it already landed on-chain (via the channel manager's cold-start mirror read) rather than building, co-signing, or submitting anything itself | Have the facilitator build+co-sign+submit the deposit group on the client's behalf, accepting partially-signed transaction bytes over the wire per the full spec | Splitting a transaction group across an HTTP trust boundary (client signs the axfer, hands raw bytes to a facilitator that adds its own signature and submits) is real, separate plumbing this pass's budget doesn't cover; the escrow-client tx builders from P1 assume one caller with all needed signers already registered on one `AlgorandClient`. Documented as a real gap for a production facilitator (one that sponsors fees or accepts unsigned groups from clients with no chain access of their own), not a silent shortcut — the demo's agent is assumed to hold funded keys and call the chain directly, which a real end-user wallet-driven agent would not want to do |
| 2026-09-11 | `BatchSettlementAvmScheme.paymentFlows` declares `"authorization"` (verify before handler, one settle call after), matching the EVM batch-settlement reference exactly | `"escrow"` (the name that sounded right for an escrow-channel design) | `@x402/core`'s `"escrow"` payment flow is a *different*, unrelated concept: it calls `beforeSettle`/`afterSettle` **twice** per request (`phase: "before-handler"` then `"after-handler"`), for two-phase settlement schemes. Picking it made our single-shot `beforeSettle` run twice, double-charging the channel (`charging 10050 would exceed signed max 10000` on the very first LocalNet demo run) until caught and fixed. The EVM reference's choice of `"authorization"` for this exact same problem was the tell — scheme *names* in this ecosystem don't always mean what they sound like; check the actual reference before assuming |
| 2026-09-11 | `BatchSettlementAvmClientScheme` signs each new voucher's ceiling off `record.signedMaxClaimable` (the latest *reserved* ceiling, written back to storage synchronously inside a per-channel lock before the request is ever sent), not off `chargedCumulativeAmount` (the confirmed actual total, only updated after a response arrives) | Use `chargedCumulativeAmount` as the signing base (matches it semantically as "how much have I used so far") | Two fields drift apart under dynamic pricing (signed ceiling is always `>=` actual charged) and, more importantly, under concurrency: using the confirmed-actual field as the signing base means two concurrent requests for the same channel can read the same stale base and sign overlapping ceilings, so whichever response lands second gets rejected for exceeding a cap the first already consumed -- reproduced on the demo with `concurrency=5`, 95/200 calls failing. Fixed by (a) using `signedMaxClaimable` as the base and (b) wrapping the read-sign-write sequence in a per-channel async lock (mirroring the server's own `ChannelStorage` lock pattern) so the reservation is atomic with respect to other in-flight requests on the same channel, regardless of how long their network round-trip takes |
| 2026-09-11 | Added a "no new charges once a pending withdrawal is within its safety margin" check to `BatchSettlementChannelManager.verifyVoucher` (rejects with the pre-existing but previously-unused `ERR.withdrawPending`; default margin 60s, configurable via `withdrawSafetyMarginSec`, injectable `now()` for testability) | Leave it unchecked (the contract's own `finalize_withdraw` already bounds how much a payer can ever be shorted, so no fund-safety issue exists) | CLAUDE.md's P5 attack list explicitly calls for "voucher during withdraw window past safety margin" to be rejected, and this was a genuine gap the adversary suite caught: before this change, the server would happily keep charging (and the client keep paying) against a channel whose payer had already signaled intent to exit, which is an availability/trust problem even though funds are never at risk. Found and fixed during P5, not before -- a concrete example of the adversary suite doing its job |
| 2026-09-11 | `packages/adversary`'s LocalNet-bound world disables the `AlgorandClient`'s suggested-params cache (`setSuggestedParamsCacheTimeout(0)`) | Leave the default cache (a few seconds) | The adversary suite fires many structurally-identical transactions back-to-back (e.g. two `settle()` calls with no varying fields). With the default cache, two such calls inside the cache window get the same `firstValid`/`lastValid` and become byte-identical (same-txid) transactions, which algod correctly rejects as `TransactionPool.Remember: transaction already in ledger` -- a harness artifact from hammering the node faster than a real client would, not a protocol issue. Reproduced directly: 2/24 attacks failed with this exact error before the fix, 24/24 passed after |
| 2026-09-11 | The adversary fuzz (`packages/adversary/src/fuzz.ts`) runs deposit/claim/stale-claim/refund/settle interleavings against real LocalNet at 500 steps by default, omitting withdraw/finalize from the op mix | Port the offline pytest fuzz's full op set (which includes withdraw/finalize via a mutable emulator clock) onto LocalNet | Advancing LocalNet's dev-mode clock costs two real transactions per attempt (set offset + a latching transaction, see the dev-mode timestamp-offset decision above), which would make withdraw/finalize disproportionately expensive inside a tight random loop; that path already has dedicated real-node coverage elsewhere (escrow-client's localnet suite for I7, the settler's I8 test), and the offline pytest fuzz (`test_fuzz_conservation`, 300 steps) already exercises it cheaply against the algopy emulator. Measured: 500 steps of the narrower op set complete in ~35-40s against real LocalNet, comfortably meeting CLAUDE.md's "≥500 steps" bar without the clock-advance op |
| 2026-09-11 | `claim()` batch size is capped by box/foreign-reference count (`MAX_APP_CALL_FOREIGN_REFERENCES`=8), exported as `MAX_CLAIM_ROWS_PER_CALL_SAME_RECEIVER`=7 (same receiver across rows) / `MAX_CLAIM_ROWS_PER_CALL`=4 (worst case, every row a different receiver); `claimBatch()` enforces the exact box-count bound rather than a flat row number | Derive the cap analytically from the opcode-budget op-up formula in CLAUDE.md §7 (`ceil(n*2600/700)` op-ups, assumed to exhaust `MAX_TRANSACTION_GROUP_SIZE`=16 around n=4) | That formula's assumption was wrong: empirically on LocalNet, n=7 claim rows (1 shared unsettled box + 7 channel boxes = 8 box refs) succeeds with no opcode-budget issue even at n=30 rows' worth of op-up fee; n=8 rows (9 box refs) fails outright with algod's literal `tx.Boxes too long, max number of box references is 8`. Opcode budget was never the binding constraint — box references were. Verified via `AlgodHTTPError`/algosdk client-side validation, not a contract-level assert, confirming it's a protocol-level txn field limit, not something `ensure_budget`'s op-up mechanism can work around |
